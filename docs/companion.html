01The database that couldn't see itselftitle
Say

This is about a gap in how we manage our Snowflake schema — and a native way to close it.

The one-line version: our repo can always build the database. Until now it could never prove the database still matches it. (beat) I'll show you what that gap costs, and then I'll close it live.

If asked
  • “DCM” = Declarative Change Management Projects, a Snowflake feature that went GA on 7 Aug 2026.
  • This is a proof of concept in a personal account — 8 tables, 53 columns, no production data.
02Our pipelines cannot see the databasethe problem
Say

Our pipelines create tables with CREATE TABLE IF NOT EXISTS — 70 of these, across 8 files.

Here's the catch. If the table already exists, that statement does nothing. It doesn't look inside. (beat) So someone adds a column by hand on a Tuesday, the pipeline re-runs, and Snowflake says “already exists, statement succeeded.” Green. Honest. And completely blind to the extra column.

No data is harmed, nothing breaks — which is exactly why it stays invisible for months.

If asked
  • “Does it recreate the table each run?” — No. First run creates; every run after is a no-op. It exists so a fresh environment builds.
  • Snowflake isn't lying — it tells you it did nothing. The defect is that “did nothing” counts as success, and nothing compares the table to what we declared.
03Only one of these was ever realtwo guarantees
Say

Two different promises here. “The repo can build the database” — always true. “The database still matches the repo” — that was never true, and nothing could tell us the difference.

(beat) For context: a dashboard in our estate sat frozen for seven months behind a check that looked like a check and never checked anything. Different bug — but the same shape.

If asked
  • By “repo” here I mean the Matillion pipeline repo that holds the 70 DDL statements — not the DCM repo.
  • The dashboard freeze was a trailing-comma syntax error hidden by an alert-then-succeed pattern. Recorded in our findings.
04Declare the state. Snowflake finds the difference.what dcm is
Say

DCM Projects is native to Snowflake — no external tool, no state file. It went GA a few weeks ago.

Instead of writing instructions, you declare what a table should look like — DEFINE, not CREATE — and Snowflake works out the difference. PLAN is a dry run that changes nothing. DEPLOY applies it.

(beat) And if you delete a table's definition, the next deploy drops the table. The file is the source of truth.

If asked
  • “vs Terraform?” — Terraform suits account-level objects and keeps an external state file; DCM is native and stateless. Common practice is both.
  • Tables, views, tasks, roles, warehouses, schemas are all GA within DCM.
05The DDL stops living inside the ETLinfrastructure as code
Say

Today our DDL lives inside the ETL — it runs as a side effect of a data load. No review, no diff, and drift is invisible.

With DCM, the DDL lives in git, reviewed like any code, and the plan shows the impact before anything lands. (beat) The database stops being a place things quietly accumulate, and becomes a build output.

If asked
  • One command rebuilds an entire environment from the repo — useful for onboarding and for standing up a fresh dev.
06The layout is fixed, not a conventionproject structure
Say

The structure is fixed — definitions must sit under sources/definitions, or Snowflake simply won't read them.

The manifest says where to deploy and what varies between environments. That's the promotion story: the same files build dev and prod, and env_suffix — _DEV or _PROD — is the only difference. (beat) Promoting to prod is just pointing the same reviewed file at a different config. You never keep a second copy of the DDL.

If asked
  • “Promotion is pointing at a target” = same definition files, run with USING CONFIGURATION PROD, which appends _PROD. No copy of the scripts to drift apart.
  • The alternative everyone lives with: a separate prod copy of the DDL that slowly diverges until nobody can reproduce prod.
07How it fits togetherarchitecture
Say

Here's the whole thing. GitHub is the source of truth. Snowflake keeps its own clone. The DCM project deploys prod from that clone — from git, never from someone's laptop.

And every night at 5, a task runs PLAN against prod, logs the result, and emails us only if something's off. (beat) PLAN is automated because it only reads. DEPLOY is a human decision — because it drops columns to fix things.

If asked
  • The clone is a GIT REPOSITORY object; it updates only on FETCH, which the nightly job runs before it plans.
  • The monitor watches prod — the thing that must match git.
08Three copies. All can be stale.three copies
Say

One thing that trips everyone up: there are three copies of these files, and all three can be stale independently. GitHub, Snowflake's clone, and my personal workspace.

A clone is a snapshot — it knows nothing about a new commit until you FETCH. (beat) GitHub is authoritative. The other two are caches.

If asked
  • A workspace lives in a per-user database — SHOW GIT REPOSITORIES won't even list it, and a scheduled task can't read it. That's why the account-level clone exists.
09A change travels one direction onlyone direction
Say

Changes only travel one way — from git, down to the database. A hand-made ALTER never flows back into the repo. There's no path back.

(beat) That asymmetry is the entire reason drift detection has to exist. If everything went through git, you wouldn't need it.

10Dev fast. Prod from git.how a developer ships
Say

So how does a developer actually work? Dev is deployed straight from the workspace — fast, no gate. Prod is deployed from git, after review, with USING CONFIGURATION PROD.

Same files build both. And because prod comes from git, git and prod agree by construction — (beat) which is what keeps the nightly check honest. If I deployed prod from my laptop and pushed afterwards, the check would flag my own deliberate change as drift.

If asked
  • Dev and prod are two databases in the same account, separated by env_suffix. No second account, no paid upgrade — just compute credits.
  • Real enterprises often split dev/prod across separate accounts — a target each. Same idea.
11Three questions. Git answers two.three diffs
Say

This is the spine of the whole idea. Three questions.

What changed in the definition? — git diff answers that. What will change in the database? — the plan answers that. What changed without going through either? (beat) That third one — that's drift. And it's the one we have never been able to see.

12Three verdicts, not twodrift detection
Say

The drift check has three verdicts, not two. Clean — matches the repo. Drift — someone changed something and it's revertible; the check names the exact column. And Error — the change can't be auto-reverted, and it may be hiding other drift.

Why three? (beat) Because 45 of our 53 columns aren't the last column in their table, and Snowflake can't reorder columns — so a dropped column usually produces Error, not Drift. A two-state monitor would read the worst case as a broken job.

If asked
  • Un-revertible cases: dropping a non-last column, narrowing a VARCHAR, renaming. Recovery is unload → drop → redeploy → reload — planned maintenance, not a 3am fix.
13It names the column · what Snowflake forgetsthe record
Say

When drift is found, the plan names the column, its type, and which way the fix goes — not just “this table differs.” That's the difference between an alert worth waking for and one people mute.

And here's a surprise: Snowflake records every deploy, but no plans at all. The drift check is the one thing it doesn't remember. (beat) So we keep our own log — which answers “when did this drift start,” the question you actually ask in an incident.

If asked
  • Measured on the account: 7+ plans, 4 deploys → history shows 4 deploys, zero plans. No ACCOUNT_USAGE view either. Re-checked after GA — still true.
14Thirteen findings. Four from deliberate sabotage.findings
Say

We found thirteen things, and four of them came from deliberately breaking it.

The verdict — yes, it detects hand-made drift, at column level. It records deploys but never plans, so an audit table is mandatory. Dropping a non-last column is un-revertible. And my favourite: (beat) our own monitor sat suspended for a day while its health view cheerfully reported “OK.”

Every failure we found was the same shape — something reporting success without checking what it claimed to check.

Say

One more thing, and it's the interesting part for us. This manages more than the shape of the tables.

The same declarative project can gate the data — quality checks declared right beside the schema. (beat) So it doesn't just prove the schema matches. It can prove the data passes.

17Quality gates, declared beside the schemabeyond schema · examples
Say

Here's what that looks like. You attach a data metric function — no null IDs, unique IDs — with an expectation. Then one command, snow dcm test, runs them all.

This is a real run: one passed, one failed, with the exact value it saw. (beat) And it exits non-zero on failure, so it gates a pipeline. Bad data caught where it enters — not three dashboards later.

If asked
  • “Enterprise only?” — No. Verified working on Standard edition.
  • Left side of an expectation is always the keyword VALUE. No subqueries, casts or arithmetic — a check, not a query.
18What it does not yet provehonest close
Say

Honestly: this is a proof of concept. One slice — eight tables, no data. Grants, tasks and streams we haven't exercised. But it proves the thing that matters.

(beat) The database can tell us, every morning, whether it still matches the repo — and name the column when it doesn't. We'd start with scheduled PLAN, which is read-only and safe. Deploy stays a human decision.
